## 各批次修改風險評估（尚未執行的批次）

風險等級：低＝改壞也容易發現與還原；中＝可能讓網站或流程無法使用；高＝可能悄悄改變數值或歷史結果。

### 第二批：安全（整體風險：低到中）

| 項目 | 可能出的問題 | 風險 | 防護做法 |
|---|---|---|---|
| 2.1 `SECRET_KEY` 改讀 `.env` | 本地 `.env` 沒設定該變數時，網站啟動失敗；更換金鑰會使既有登入 session 失效 | 中 | 先在 `.env.example` 補欄位並通知使用者設定；程式讀不到時給明確錯誤訊息，或開發環境才允許預設值 |
| 2.2 `DEBUG`、`ALLOWED_HOSTS` 改由環境變數控制 | `DEBUG=False` 時 Django 不再提供靜態檔，CSS 會消失；`ALLOWED_HOSTS` 漏填會回 400 | 中 | 預設維持目前行為（本機 `DEBUG=True`），只有明確設定才切換；對外部署時另行處理靜態檔 |
| 2.3 網頁按鈕加登入保護 | 尚未建立帳號就無法使用「執行預測」「更新股價」等按鈕；既有的 `tests_stock_import` 若呼叫這些 view 會變成 302 | 中 | 先 `createsuperuser`、補登入頁；同步更新受影響的測試；改動前確認使用者本機有帳號 |
| 2.4 執行鎖改用資料庫或檔案鎖 | 新鎖異常時（例如程式中途被關閉）會殘留，導致之後永遠顯示「執行中」 | 低到中 | 鎖設逾時（現有為 1800 秒）並提供手動清除方式 |

不影響任何預測、回測數值。主要風險是「網站打不開」或「按鈕不能用」，可在本地開頁面立即發現。

### 第三批：維護性（整體風險：中到高，建議最後才做）

| 項目 | 可能出的問題 | 風險 | 防護做法 |
|---|---|---|---|
| 4.2 新增 CI | CI 環境無 MySQL 與 `mysqlclient`，可能一開始就失敗；失敗只影響檢查，不影響專案本身 | 低 | 使用 SQLite 測試設定；先在分支驗證 |
| 4.3 新增無未來資料洩漏測試 | 測試寫錯會誤判；若測出真的有洩漏，代表既有結果需重新檢討 | 低（但可能揭露問題） | 先以小資料驗證測試本身能抓到「故意洩漏」的案例 |
| 3.1 抽共用特徵模組 | **最危險**：特徵計算差一個小數，預測與回測結果就會改變，V5.9 歷史數字無法再對照；兩份程式現有細微差異（資料來源、欄位處理）可能被合併時抹掉 | 高 | 必須先寫「重構前後逐列輸出相同」的測試，並比對 `myapp/ml/output/` 各 CSV 雜湊；未通過就不合併；不修改既有檔案的輸出格式 |
| 3.2 拆分 `views.py` | import 路徑改變，`urls.py` 或模板漏改會造成頁面 500；遺漏某個 view | 中 | 每頁做冒煙測試（回 200）再拆；不改 URL 與模板 |
| 3.3 長任務改背景執行 | 狀態顯示錯誤、同時啟動兩個任務、失敗無提示；與現有 `stock_queue.py` 互相影響 | 中 | 沿用既有 `stock_queue.py` 模式；保留逾時與鎖；失敗寫入 log |
| 1.4 `config.py` 延遲載入 | `config.py` 被多支腳本與模型 import，改動載入時機可能讓股票池變空而**不報錯**，導致選股結果悄悄改變 | 高 | 加測試確認股票池內容與改前一致；空池仍須警告 |
| 1.5 新增 Windows 排程腳本 | 路徑、編碼、環境變數與 `run_daily.sh` 行為不一致，造成每日流程漏步驟 | 中 | 新增檔案不取代舊檔；先手動跑一次比對日誌 |

### 第四批：資料與模型研究（對既有結果風險：低；對結論風險：高）

| 項目 | 可能出的問題 | 風險 | 防護做法 |
|---|---|---|---|
| 5.1 補歷史成分股 | 資料來源不完整或日期對不上，反而引入錯誤；`USE_POOL_START` 一旦開啟，既有回測數字會改變 | 高 | 以新版本與獨立輸出進行；取不到完整資料就停止，不用替代資料 |
| 5.2 擴充更早年份 | 除權息與還原價在舊年份缺漏，造成報酬計算錯誤；匯入資料量大，可能觸發 428 限流 | 中 | 分批匯入、先跑價格缺漏與還原跳動檢查；失敗不覆寫現有 `adjusted_prices.csv` |
| 5.3 加入加權指數 | 與 0050 的日期對不齊 | 低 | 僅作第二基準報告，不改主結果 |
| 6.1 加入月營收特徵 | **公告日對齊錯誤 = 未來資料洩漏**，回測會虛高；也會改變 `FEATURE_COLUMNS`，兩份程式必須同步 | 高 | 以公告日（含法定延遲）後才可使用；新版本號；先寫洩漏測試 |
| 6.2 改預測超額報酬／排名 | 屬新模型，需完整 walk-forward；比較時易有多重檢定問題 | 高 | 事先寫規格與固定參數；不為提高績效挑目標函數 |
| 6.3 權重上限 | 容易變成為績效而挑上限值 | 中 | 上限值於看結果前固定，並記錄 |
| 6.4 空頭濾網前瞻版 | 與 V5.9-FORWARD 共用資料表時可能誤寫既有紀錄 | 中 | 使用獨立版本號（`model_version`）與獨立輸出；不改既有紀錄 |
| 6.5 證交稅敏感度 | 無（僅報告） | 低 | 不改主結果 |

> 這些項目的共同風險是「結果變好看」不等於「真的更好」：樣本僅 65 期、有存活者偏差，任何改善都可能是偶然。

### 通用保護原則

1. 每批使用獨立分支，使用者本地驗證通過才合併到 `main`。
2. 改動前先記錄 `myapp/ml/output/` 各 CSV 的雜湊，改動後比對；既有輸出必須逐檔相同。
3. 改動後執行 `python manage.py test myapp`（目前 33 項），並開啟網站各頁確認。
4. 與模型或策略參數有關的改動，先寫規格與固定參數，再看結果。
5. 第三批若無法先補齊保護測試，則不執行。
